# D3 · 실제 사용자 Job-to-be-done, 대안 및 비용
조사일 2026-11-16 · **확보된 실제 E1 고객 = INC-01, E2 목표 사건 = 0**

## 사용자의 실제 Job (INC-01 직접 보고 범위)
- **사용자:** 여러 고객에게 컴퓨터 비전 모델 하나를 배포·유지하는 개발자(기업 이름/실제 고객 수 미공개).
- **문제 유발 변경:** 한 고객에서 얻은 데이터를 공통 모델 재학습에 반영할 때 다른 고객에서 불필요한 검출/새 실패가 나타날 수 있음.
- **이 업무의 목적:** 모델을 모든 고객에 신속하게 업데이트하되 고객별 회귀를 막는 것.
- **현재 수단:** 전체 고객에 대한 회귀 검사 필요하다고 본인이 설명. **현행 도구 이름·설정·실제 운영 비용/시간 미공개.**
- **고민 중인 대안:** 공통 backbone 후 고객별/그룹별 fine-tune. 단점: 모델/학습 과정 수 증가. 실행했다는 확인 없음.
- **우리 제품의 가설:** 필요한 고객을 학습 변경으로 사전 추정→동일 예산에서 신규 고위험 회귀를 더 일찍 찾되 무작위 표본/UNTESTED로 불확실성을 보존.
- **반증:** FiftyOne+일반 Python의 per-customer slice/CI, Roboflow의 customer eval suites, AWS/직접 per-tenant 모델 버전 분리로 충분한 경우 ChangeScope standalone 불필요.
- **대안 비용/ROI:** 사내 교육비·추론 단가·검수자 시간·모델 운영 TCO는 전부 UNKNOWN. AWS 합성 데모 $0.07을 고객 경제성의 정량 근거로 사용 금지.

## 실제 고객이 확인되지 않은 판단 인터뷰/추적 항목 (미수행)
1. 한 고객 모델 데이터 추가의 빈도·검수 대상 고객 수·고객별 클래스 차이가 얼마나 되는가?
2. 전체 회귀검사 시간을 어느 단계(이미지 추론/사람 정답/테스트 suite 정리/배포 승인)에서 보내는가?
3. 공통 backbone + per-tenant fine-tuning, 병렬 평가, 캐싱, incremental test selection을 실제 시도했는가?
4. FiftyOne, Roboflow, SageMaker를 실제 사용했는가? 했다면 버전·플랜·시도 설정과 여전히 남은 장애는?
5. 어느 수준의 놓친 회귀 비용이 크며, 실행·라벨 검수 예산은 어떻게 제한되는가?
6. 데이터 접근권/원본 이미지 반출 제약으로 중앙 클라우드 평가가 불가능한가?

**동일 사용자 답이 확인되기 전까지 이 질문의 답과 구매 의사/예산은 UNKNOWN.**

## 경제적 가설과 측정
- 사례 추후 실증 시 `release regression time = data preparation + model inference + human adjudication + CI & approval`; 모든 구성요소를 실제 계측.
- 동일 사용자 동일 업무 기준 비교: FiftyOne+reasonable scripts, Roboflow Eval/checks, per-tenant models; ChangeScope 측정값은 아직 0.
- 제안 목표: 같은 검사 예산에서 가장 큰 모델 회귀 이벤트를 더 적은 사람 분으로 확인, 중대 오류 미검출률 악화 없음, 고객별 UNTESTED 범위를 정직하게 공개. 목표치는 사용자 수용 기준 확인 전 임의 설정 금지.
- 부정 결과 시: 복수 고객 데이터의 보관·독립 GT 비용이 신규 제품 가치보다 크면 NO-GO.
